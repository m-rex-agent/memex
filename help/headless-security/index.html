Erişim anahtarlarını koru

memex-mcp'yi memex uygulaması olmadan, kendi başına çalıştırıyorsan erişim anahtarların varsayılan olarak korunmaz. Bu sayfa anahtarları nasıl koruyacağını ve her koruma düzeyinin neyi durdurup neyi durdurmadığını anlatır.

“Erişim anahtarları korunmuyor” ne demek?

Sunucu açılırken şu üç satırı yazıyorsa anahtarların korumasızdır:

memex-mcp: access keys are NOT protected — any program running as this user could add an admin key.
Protect them:  memex-mcp trust init
Guide:         https://m-rex-agent.github.io/memex/help/headless-security/

Kimin ne yapabileceğini üç dosya belirler: tokens.json (anahtarlar), remotes.json (bulutlar) ve policy.yaml (kurallar). Hepsi yapılandırma klasöründedir. Koruma yokken bu kullanıcı olarak çalışan herhangi bir program bu dosyalara yazıp kendine yönetici anahtarı ekleyebilir. Koruma açıkken sunucu her dosyadaki imzayı doğrular; imzası eksik ya da yanlış olan dosyaya güvenmez. Güvenilmeyen tokens.json hiçbir anahtarı tanımaz, güvenilmeyen remotes.json hiçbir bulut yüklemez, güvenilmeyen policy.yaml her şeyi reddeder.

İmzayı üreten gizli anahtar yapılandırma klasöründe tutulmaz, ayrı bir dosyada durur. Korumanın gücü bu dosyayı kimin okuyabildiğine bağlıdır.

Üç koruma düzeyi

  1. Hiçbir şey. Sunucu uyarıyı yazar ve çalışır. Bu kullanıcı olarak çalışan her program yönetici anahtarı ekleyebilir.
  2. trust init. Gizli anahtar dosyasını oluşturur ve üç dosyayı imzalar. Dosyalara gizli anahtarı bilmeden yazan bir program artık işe yaramaz: sunucu yazılanı reddeder. Gizli anahtar dosyasını diğer kullanıcılar okuyamaz. Durdurmadığı şey: sunucuyla aynı kullanıcı olarak çalışan bir program gizli anahtar dosyasını da okuyabilir ve geçerli imza üretebilir.
  3. Ayrı hizmet kullanıcısı. Sunucuyu yalnızca bu iş için açılmış bir hesapla çalıştırırsın ve gizli anahtar dosyası o hesaba (ya da root'a) ait olur. Senin kullanıcın olarak çalışan programlar gizli anahtarı okuyamaz, yapılandırma klasörüne yazamaz. Durdurmadığı şey: hizmet kullanıcısı olarak ya da root olarak çalışan bir program korumayı aşar. Bu düzey, bilgisayarındaki diğer programlarla sunucu arasına sınır koyar; sunucu hesabının kendisini ele geçirene karşı koruma sağlamaz.

1. adım: trust init

memex-mcp trust init

Komut sırasıyla şunları yapar:

  • Gizli anahtarı yapılandırma klasörünün içindeki trust.secret dosyasına yazar (yalnızca sahibi okuyabilir). Anahtarı ekrana yazmaz. Başka bir yer istersen --secret-file <yol> ekle.
  • tokens.json, remotes.json ve policy.yaml dosyalarını imzalar. Henüz var olmayan dosyayı sunucu kendisi oluştururken imzalar.
  • Sunucuyu nasıl başlatacağını yazar.

Dosyalardan biri zaten imzalıysa komut hiçbir şeyi değiştirmeden durur ve trust rotate komutunu önerir. Yarıda kalmış bir trust init'i aynı komutla yeniden çalıştırabilirsin: daha önce yazdığı gizli anahtarı kullanır ve kaldığı yerden devam eder.

Sunucuyu gizli anahtarla başlat:

memex-mcp --trust-secret-file /yol/trust.secret

ya da yolu bir ortam değişkeniyle ver (değişken yalnızca yolu taşır, anahtarı değil):

MEMEX_MCP_TRUST_SECRET_FILE=/yol/trust.secret memex-mcp

Gizli anahtar dosyası 64 küçük harfli onaltılık karakter içermeli; POSIX'te kipi 0600 olmalı ve sunucuyu çalıştıran kullanıcıya ait olmalıdır (Windows'ta yalnızca sahibi, SYSTEM ve Administrators erişebilir). Sunucunun kullanamadığı bir dosya verirsen sunucu açılmaz (çıkış kodu 2); böylece bir yazım hatası korumayı hiçbir zaman sessizce kapatmaz. Gizli anahtar hiç verilmezse sunucu korumasız çalışır.

Yapay zekâ araçlarının başlattığı sunucular (stdio) gizli anahtar istemez; bulut işlemlerini anahtarları tutan sunucuya iletir ve kararı o sunucu verir.

İmzalı bir kurulumda memex-mcp token list, token mint ve token revoke komutlarına da gizli anahtarı ver (--trust-secret-file <yol> ya da aynı ortam değişkeni). Vermezsen komut dosyaya dokunmadan durur.

Kararını bekleyen bulutlar

trust init, remotes.json içindeki her bulutu kontrol eder. Kendi bölümü olmayan, kısıtsız bir sarmalayıcı olan ya da izin verilmeyen seçenek taşıyan bulut imzalanmaz; silinmez ve yüklenmez, sebebiyle birlikte remotes.held.json dosyasına kenara ayrılır. Baştan bildiğin bir bulutu imzalamak için --keep ekle (birden çok kez kullanılabilir):

memex-mcp trust init --keep drive --keep arsiv

Sonradan karar vermek için:

memex-mcp trust held list
memex-mcp trust held keep <bulut-kimliği>
memex-mcp trust held keep <bulut-kimliği> --acknowledge-risk
memex-mcp trust held remove <bulut-kimliği>
memex-mcp trust held keep-policy
memex-mcp trust held remove-policy

keep, bulut kontrolden geçerse onu imzalar ve devreye alır. Kontrolden geçmeyen bir bulutu yine de kullanmak için --acknowledge-risk ekle; böylece o bulutun kısıtsız erişimini bilerek kabul edersin. remove kenara ayrılan kaydı siler. keep-policy ve remove-policy kenara ayrılan kural dosyası için aynı kararı verir. Bu komutlar gizli anahtarı ister (--secret-file ile ya da varsayılan konumdan); ardından çalışan sunucuyu yeniden başlat.

2. adım: ayrı hizmet kullanıcısı

Aşağıdaki kurulumların hepsi için önce trust init çalıştır, sonra dosyaları üret:

memex-mcp trust service-files ./hizmet

Komut bulunduğun işletim sistemi için dosyaları gerçek yollarınla doldurur ve kurulum ile kaldırma satırlarını ekrana yazar. Hiçbir şey kurmaz, sistemde hiçbir şeyi değiştirmez. Başka bir sistem için dosya üretmek istersen --os linux|darwin|win32 ekle. Komut, sunucunun kullanacağı kasayı bulamazsa durur: MEMEX_VAULT_PATH ayarla ya da --vault <yol> ver. İlk çalıştırmada ikisini tek komutla yapabilirsin: memex-mcp trust init --service-files ./hizmet. Her kurulum satırının yanında onu birebir geri alan bir kaldırma satırı yazılır; kurulumu geri almak için bu satırları ters sırayla çalıştır.

Linux (systemd)

Üretilen memex-mcp.service birimi hizmeti memex adlı kullanıcı olarak çalıştırır, gizli anahtarı systemd'ye yalnızca bu hizmete özel bir bellek alanına kopyalatır (LoadCredential=) ve sunucuyu --trust-secret-file ${CREDENTIALS_DIRECTORY}/memex-trust ile başlatır. Kurulum satırları şunları yapar:

  • memex kullanıcısını oluşturur (bu kullanıcı oturum açamaz).
  • Yapılandırma klasörünü /var/lib/memex-mcp altına taşır (hizmet kullanıcısı senin /home altındaki ana klasörüne giremez). Gizli anahtar dosyası root'a ait kalır. Hizmet ortamında MEMEX_MCP_CONFIG_DIR=/var/lib/memex-mcp ayarlıdır.
  • memex kullanıcısına kasada ve kasaya giden yoldaki klasörlerde gereken erişimi verir.
  • Birimi /etc/systemd/system altına kopyalar ve systemctl enable --now memex-mcp ile başlatır.

Hizmetin yapılandırması üzerinde bir komut çalıştırmak için (örneğin durum kontrolü) klasörü ve gizli anahtarı ver; trust service-files bu satırın aynısını kurulum satırlarından sonra da yazar:

sudo env MEMEX_MCP_CONFIG_DIR=/var/lib/memex-mcp memex-mcp trust status --secret-file /var/lib/memex-mcp/trust.secret

macOS (launchd)

Üretilen dev.memex.mcp.plist dosyası sunucuyu _memex adlı gizli bir hizmet hesabı olarak çalıştırır. Hesap giriş ekranında görünmez ve oturum açamaz; kimliği 450–499 aralığındaki ilk boş değerdir (macOS 27'de zorunlu aralık budur, eski sürümlerde 200–400 kullanılırdı; gerekirse ilk kurulum satırındaki aralığı düzenle). Kurulum satırları hesabı sysadminctl ile oluşturur (yönetici parolası sorabilir), yapılandırma klasörünü ve gizli anahtar dosyasını bu hesaba verir, kasaya bu hesap için bir erişim kuralı ekler, plist'i /Library/LaunchDaemons altına koyar ve launchctl bootstrap system ile başlatır.

  • Kasayı Masaüstü, Belgeler ve İndirilenler dışında tut: macOS arka plan hizmetlerinin bu klasörlere girmesini engeller.
  • Gizli anahtar dosyası artık _memex hesabına aittir (kip 0600). Hizmetin yapılandırması üzerinde bir komut çalıştırmak için: sudo -u _memex env MEMEX_MCP_CONFIG_DIR=<yapılandırma klasörü> memex-mcp trust status --secret-file <gizli anahtar yolu>

Windows (hizmet)

trust service-files bir memex-mcp-windows-service.txt dosyası yazar: hizmetin ortam değişkenleri, komut satırı, kurulum ve kaldırma adımları. Adımlar memex adlı bir kullanıcı oluşturur, gizli anahtar dosyasının sahibini ve izinlerini yalnızca bu kullanıcı erişecek şekilde ayarlar (SYSTEM ve Administrators dışında başka hesap erişemez), yapılandırma klasörüne ve kasaya yazma izni verir, sonra hizmeti sc.exe ile oluşturur. Bilmen gereken üç şey:

  • Node bir hizmet sarmalayıcısı olmadan Windows hizmeti olarak çalışmaz. sc.exe start hata 1053 verir. memex-mcp ile birlikte sarmalayıcı gelmez; WinSW ya da NSSM gibi seçtiğin bir sarmalayıcıyı dosyadaki komut satırı ve ortam değişkenleriyle kur. sc.exe satırları hesabı, dosya izinlerini ve bağımsız değişkenleri gösterir.
  • İlk başlatmadan önce memex kullanıcısına “Hizmet olarak oturum açma” (Log on as a service) hakkını ver: secpol.msc → Yerel İlkeler → Kullanıcı Hakları Ataması. sc.exe create bunu vermez.
  • Adımları yükseltilmiş (yönetici) bir komut isteminde çalıştır.

Docker

Gizli anahtar dosyasının sunucuyu çalıştıran kullanıcıya ait olması ve yalnızca ona açık olması gerekir. Docker'ın varsayılan gizli dosyaları (/run/secrets/…) root'a aittir ve herkes tarafından okunabilir; sunucu böyle bir dosyayı reddeder ve açılmaz. Bunun yerine sahibi kapsayıcıdaki kullanıcı olan, kipi 0600 olan bir dosyayı bağla.

  1. Ana makinede, kapsayıcıya bağlayacağın yapılandırma klasörüyle trust init çalıştır: 
    MEMEX_MCP_CONFIG_DIR=$PWD/config memex-mcp trust init --secret-file $PWD/trust.secret
  2. Dosyaları kapsayıcının kullanıcısına ver (aşağıdaki örnekte 1000): 
    sudo chown 1000:1000 $PWD/trust.secret $PWD/config
sudo chmod 600 $PWD/trust.secret
  3. Kapsayıcıyı aynı kullanıcıyla çalıştır, dosyayı salt okunur bağla ve yolunu ortam değişkeniyle ver: 
    docker run --user 1000:1000 \
  -v $PWD/config:/config -v $PWD/trust.secret:/run/memex/trust.secret:ro \
  -e MEMEX_MCP_CONFIG_DIR=/config \
  -e MEMEX_MCP_TRUST_SECRET_FILE=/run/memex/trust.secret \
  <memex-mcp-imajın>

Docker Compose'un secrets: bölümü Swarm dışında dosyanın sahibini ve kipini değiştirmez; bu yüzden dosyayı yukarıdaki gibi bağla.

Gizli anahtarı değiştir: trust rotate

memex-mcp trust rotate

Komut yeni bir gizli anahtar üretir, eski anahtarla doğrulanan her dosyayı yeni anahtarla yeniden imzalar ve gizli anahtar dosyasını tek adımda değiştirir. Bittikten sonra sunucuyu yeniden başlat; çalışan sunucu yeni anahtarı kendiliğinden okumaz.

  • Yarıda kalırsa: yeni anahtar trust.secret.next dosyasında bekler ve trust status ve sunucu açılırken “rotation incomplete — run memex-mcp trust rotate” yazar. Komutu yeniden çalıştırman yeter: kaldığı yerden devam eder.
  • Hiçbir dosya doğrulanmıyorsa (örneğin anahtar dosyası başka bir kurulumdan geldiyse) komut hiçbir şeyi değiştirmeden durur. Anahtarı yine de değiştirmek istersen --force ekle. Doğrulanmayan dosyalar olduğu gibi kalır ve sunucu onları reddetmeyi sürdürür.
  • Gizli anahtarı kaybettiysen rotate işe yaramaz (eskisini okuması gerekir); trust reset kullan. Komut yalnızca gizli anahtar dosyası yoksa ya da hiçbir dosyayı doğrulamıyorsa çalışır. Önce memex-mcp trust reset çalıştır: hiçbir şeyi değiştirmeden ne olacağını gösterir. Onaylıyorsan memex-mcp trust reset --yes çalıştır (başka bir gizli anahtar yolu için --secret-file <yol>). Komut şunları yapar:
    • Tüm erişim anahtarları iptal edilir; tokens.json'un yedeği saklanır. Yeni bir yönetici anahtarı üret ve yapay zekâ araçlarını yeniden bağla: memex-mcp token mint --kind admin --trust-secret-file <yol>
    • Bulutlar ve kurallar silinmez, kenara ayrılır. Her birine memex-mcp trust held list, keep ve remove ile karar ver.
    • Yeni bir gizli anahtar oluşturulur ve her şey onunla imzalanır. Eski gizli anahtar dosyası <gizli anahtar>.lost-<sayı> adıyla saklanır; kaybolduğundan emin olunca sil.
    • Sunucuyu yeni gizli anahtarla yeniden başlat.

Durumu gör: trust status

memex-mcp trust status
Trust secret file: /var/lib/memex-mcp/trust.secret
  present, permissions ok
Trust files:
  tokens.json        signed (verified)  mode 0600
  remotes.json       signed (verified)  mode 0600
  policy.yaml        signed (verified)  mode 0600

Komut her dosyanın imzasının doğrulanıp doğrulanmadığını, dosya kiplerini ve gizli anahtar dosyasının izinlerini gösterir; gizli anahtarı yazmaz. Her şey doğruysa çıkış kodu 0, aksi hâlde 1'dir. Çalışan bir sunucunun korunup korunmadığını GET /health yanıtındaki "trust" alanından da görebilirsin: signed korumalı, unsigned korumasızdır.

Server · headless setup

Protect your access keys

If you run memex-mcp on its own, without the memex app, your access keys are not protected by default. This page shows how to protect them and what each level of protection does and does not stop.

What “access keys are NOT protected” means

If the server prints these three lines when it starts, your keys are unprotected:

memex-mcp: access keys are NOT protected — any program running as this user could add an admin key.
Protect them:  memex-mcp trust init
Guide:         https://m-rex-agent.github.io/memex/help/headless-security/

Three files decide who can do what: tokens.json (keys), remotes.json (clouds) and policy.yaml (rules). All three live in the config folder. With no protection, any program running as this user can write to them and give itself an admin key. With protection on, the server checks a signature on each file and does not trust a file whose signature is missing or wrong. An untrusted tokens.json recognizes no key, an untrusted remotes.json loads no cloud, and an untrusted policy.yaml denies everything.

The secret that makes the signature is not kept in the config folder. It sits in a separate file, so the protection is only as strong as the list of who can read that file.

The three levels

  1. Nothing. The server prints the warning and runs. Any program running as this user can add an admin key.
  2. trust init. Creates the secret file and signs the three files. A program that writes to the files without knowing the secret no longer works: the server rejects what it wrote. Other users cannot read the secret file. What it does not stop: a program running as the same user as the server can read the secret file too, and can produce a valid signature.
  3. A dedicated service user. You run the server as an account made only for it, and the secret file belongs to that account (or to root). Programs running as your own user cannot read the secret or write to the config folder. What it does not stop: a program running as the service user, or as root, gets around it. This level puts a boundary between the server and the other programs on the machine; it does not protect against someone who takes over the server account itself.

Step 1: trust init

memex-mcp trust init

The command, in order:

  • Writes the secret to trust.secret inside the config folder (readable by its owner only). It never prints the secret. To put it elsewhere, add --secret-file <path>.
  • Signs tokens.json, remotes.json and policy.yaml. A file that does not exist yet is signed by the server when it creates it.
  • Prints how to start the server.

If any of the files is already signed, the command stops without changing anything and points you to trust rotate. You can run an interrupted trust init again: it uses the secret it already wrote and carries on.

Start the server with the secret:

memex-mcp --trust-secret-file /path/to/trust.secret

or give the path in an environment variable (the variable holds the path only, never the secret):

MEMEX_MCP_TRUST_SECRET_FILE=/path/to/trust.secret memex-mcp

The secret file must hold 64 lowercase hex characters. On POSIX its mode must be 0600 and it must belong to the user running the server (on Windows only its owner, SYSTEM and Administrators may have access). If you give a file the server cannot use, the server does not start (exit code 2), so a typo never switches protection off quietly. If you give no secret at all, the server runs unprotected.

Servers that an AI tool starts (stdio) need no secret. They pass cloud operations to the server that holds the keys, and that server makes the decision.

On a signed install, give the secret to memex-mcp token list, token mint and token revoke too (--trust-secret-file <path> or the same variable). Without it the command stops and leaves the file alone.

Held clouds

trust init checks every cloud in remotes.json. A cloud that has no section of its own, is an unconfined wrapper, or carries an option that is not allowed is not signed. It is set aside in remotes.held.json with its reason: not deleted, not loaded. To sign in a cloud you know up front, add --keep (repeatable):

memex-mcp trust init --keep drive --keep archive

To decide later:

memex-mcp trust held list
memex-mcp trust held keep <cloud-id>
memex-mcp trust held keep <cloud-id> --acknowledge-risk
memex-mcp trust held remove <cloud-id>
memex-mcp trust held keep-policy
memex-mcp trust held remove-policy

keep signs the cloud in and puts it to use if it passes the check. To use a cloud that fails the check anyway, add --acknowledge-risk; that means accepting its unconfined reach on purpose. remove deletes the held record. keep-policy and remove-policy make the same decision for a held rules file. These commands need the secret (--secret-file, or the default location) and a restart of the running server.

Step 2: a dedicated service user

For every setup below, run trust init first, then generate the files:

memex-mcp trust service-files ./service

The command fills the files in with your real paths for the system you are on and prints the install and removal lines. It installs nothing and changes nothing on the system. To generate files for another system, add --os linux|darwin|win32. If it cannot find the vault the server will use, it stops: set MEMEX_VAULT_PATH or pass --vault <path>. On a first run you can do both at once: memex-mcp trust init --service-files ./service. Every install line comes with an exact undo line; run them in reverse order to take the setup back.

Linux (systemd)

The generated memex-mcp.service runs as a user named memex, has systemd copy the secret into a private memory area for this service only (LoadCredential=), and starts the server with --trust-secret-file ${CREDENTIALS_DIRECTORY}/memex-trust. The install lines:

  • Create the memex user (it cannot log in).
  • Move the config folder to /var/lib/memex-mcp (the service user cannot enter your home folder under /home). The secret file stays owned by root. The service environment sets MEMEX_MCP_CONFIG_DIR=/var/lib/memex-mcp.
  • Give memex the access it needs to the vault and the folders on the way to it.
  • Copy the unit into /etc/systemd/system and start it with systemctl enable --now memex-mcp.

To run a command against the service’s config (a status check, for example), give the folder and the secret. trust service-files prints this exact line after the install lines too:

sudo env MEMEX_MCP_CONFIG_DIR=/var/lib/memex-mcp memex-mcp trust status --secret-file /var/lib/memex-mcp/trust.secret

macOS (launchd)

The generated dev.memex.mcp.plist runs the server as a hidden service account named _memex. The account does not appear on the login window and cannot log in; its ID is the first free one between 450 and 499 (macOS 27 requires that range; older releases used 200–400, so edit the range in the first install line if you need to). The install lines create the account with sysadminctl (it may ask for an administrator password), give it the config folder and the secret file, add an access rule for it on the vault, put the plist in /Library/LaunchDaemons and start it with launchctl bootstrap system.

  • Keep the vault outside Desktop, Documents and Downloads: macOS stops background services from entering those folders.
  • The secret file now belongs to _memex (mode 0600). To run a command against the service’s config: sudo -u _memex env MEMEX_MCP_CONFIG_DIR=<config folder> memex-mcp trust status --secret-file <secret path>

Windows (service)

trust service-files writes a memex-mcp-windows-service.txt file with the service’s environment variables, its command line, and the install and removal steps. The steps create a user named memex, set the secret file’s owner and permissions so only that user has access (apart from SYSTEM and Administrators), grant write access to the config folder and the vault, and create the service with sc.exe. Three things to know:

  • Node cannot run as a Windows service without a service wrapper. sc.exe start fails with error 1053. memex-mcp ships no wrapper; set up one you choose, such as WinSW or NSSM, with the command line and environment variables from the file. The sc.exe lines show the account, the file permissions and the arguments.
  • Before the first start, give memex the “Log on as a service” right: secpol.msc → Local Policies → User Rights Assignment. sc.exe create does not grant it.
  • Run the steps in an elevated (administrator) prompt.

Docker

The secret file must belong to the user running the server and be open to that user only. Docker’s default secret files (/run/secrets/…) belong to root and are readable by everyone; the server refuses such a file and does not start. Mount a file owned by the container’s user with mode 0600 instead.

  1. On the host, run trust init with the config folder you will mount into the container: 
    MEMEX_MCP_CONFIG_DIR=$PWD/config memex-mcp trust init --secret-file $PWD/trust.secret
  2. Give the files to the container’s user (1000 in the example below): 
    sudo chown 1000:1000 $PWD/trust.secret $PWD/config
sudo chmod 600 $PWD/trust.secret
  3. Run the container as that user, mount the file read-only and give its path in the environment variable: 
    docker run --user 1000:1000 \
  -v $PWD/config:/config -v $PWD/trust.secret:/run/memex/trust.secret:ro \
  -e MEMEX_MCP_CONFIG_DIR=/config \
  -e MEMEX_MCP_TRUST_SECRET_FILE=/run/memex/trust.secret \
  <your-memex-mcp-image>

Outside Swarm, Docker Compose’s secrets: section does not change a file’s owner or mode, so mount the file as shown above.

Change the secret: trust rotate

memex-mcp trust rotate

The command makes a new secret, signs every file that verifies under the old secret again with the new one, and replaces the secret file in one step. Restart the server afterwards; a running server does not pick up the new secret by itself.

  • If it stops half-way, the new secret waits in trust.secret.next, and trust status and the server’s start-up say “rotation incomplete — run memex-mcp trust rotate”. Run the command again: it carries on from where it stopped.
  • If no file verifies (for example the secret file came from another install), the command stops and changes nothing. To replace the secret anyway, add --force. Files that do not verify stay as they are, and the server keeps rejecting them.
  • If you have lost the secret, rotate cannot help (it has to read the old one); use trust reset. It only runs when the secret file is missing or verifies no file. First run memex-mcp trust reset: it shows what will happen and changes nothing. If you agree, run memex-mcp trust reset --yes (add --secret-file <path> for a different secret path). The command:
    • Revokes all access keys and keeps a backup of tokens.json. Mint a new admin key and reconnect your AI tools: memex-mcp token mint --kind admin --trust-secret-file <path>
    • Sets clouds and rules aside, not deleted. Decide each with memex-mcp trust held list, keep and remove.
    • Creates a new secret and signs everything with it. The old secret file is kept as <secret>.lost-<number>; delete it once you are sure it is lost.
    • Restart the server with the new secret.

See where you stand: trust status

memex-mcp trust status
Trust secret file: /var/lib/memex-mcp/trust.secret
  present, permissions ok
Trust files:
  tokens.json        signed (verified)  mode 0600
  remotes.json       signed (verified)  mode 0600
  policy.yaml        signed (verified)  mode 0600

It shows whether each file’s signature verifies, the file modes and the secret file’s permissions. It never prints the secret. The exit code is 0 when everything verifies and 1 otherwise. For a running server, the "trust" field of GET /health tells you the same: signed is protected, unsigned is not.
